# 포트폴리오 웹사이트 + 면접 Q&A 챗봇 진행 계획

> 목표: Notion 포트폴리오를 웹사이트로 옮기고, 면접관이 "이 프로젝트에서 뭘 했나요?"라고 물으면 답하는 챗봇을 붙인다.
> 이 사이트 자체가 **웹 프론트엔드 역량을 보여주는 대표 프로젝트**가 되도록 만든다.

## 0. 현황 요약 (Notion 점검 결과)

| 구분 | 프로젝트 |
| --- | --- |
| 웹 (React) | 모두의 입시 AI ((주)이노스피치) |
| iOS 회사 | 피카로카, 저축하나로 ((주)피카로카) / 볼텍스 게이밍, 인벤 ((주)인벤) / 모먼트핀 |
| iOS 사이드 | 피피, 모두의 지하철, 북서치, 투두리스트(ToDoList), 웨더메이트(WeatherMate) |
| React Native | 체크잇, 하이브리드앱, 트립로그(비공개) |

- Notion에 갤러리 DB가 **3개** 있고, 같은 프로젝트가 서로 다른 태그/유형으로 중복 등록돼 있음 → 정리 필요
- 웹 프론트엔드 경력을 보여주는 프로젝트는 현재 **1개**(모두의 입시 AI). 대신 이 프로젝트는 개발 사항·회고(토글 7개)가 아주 상세함
- 각 프로젝트 상세 페이지에 회고 토글, 스크린샷, column 레이아웃 이미지가 있음 → 내보내기 시 이미지 누락 주의

## 1. 이전 대화 점검

**그대로 가져갈 것 (타당함)**
- API 키는 서버 라우트(`/api/chat`)에서만 사용, 브라우저 노출 금지
- 프로젝트 수가 적으므로 RAG/벡터 DB 없이 **전체 데이터를 시스템 프롬프트에 넣는 방식**
- 할루시네이션 방지 규칙("모르면 지원자에게 직접 물어봐 달라"), 무관한 질문 거절
- IP 기반 요청 제한, 최대 토큰 제한, 소형 모델
- 프로젝트별 "이 프로젝트에 대해 물어보기" 버튼, 추천 질문 칩
- 설계 결정을 README에 정리해 면접 소재로 활용

**보완할 것 (이전 대화에서 빠졌거나 실제 내용과 맞지 않는 부분)**
1. **포지셔닝**: 웹 FE 지원인데 프로젝트 대부분이 iOS → 사이트 구성과 챗봇 답변 모두 "웹 FE 중심, 모바일 경험은 강점으로" 전략이 필요
2. **콘텐츠와 챗봇 데이터 이중 관리 위험**: 화면용 / 챗봇용 데이터를 따로 쓰면 내용이 어긋남 → 프로젝트당 파일 하나(MDX + frontmatter)를 **단일 원본**으로 두고 화면과 챗봇이 함께 읽도록 구성
3. **Notion 토글 회고 내용**: 챗봇 답변 품질의 핵심 소스인데, 내보내기 후 누락되기 쉬움 → 별도 확인 항목으로 둠
4. **회사 프로젝트 보안**: 회사 내부 정보(API 규칙, 내부 지표 등)가 챗봇을 통해 노출될 수 있음 → 공개 가능 범위 검토
5. **비용 상한**: 요청 제한만으로는 부족 → LLM 제공사 콘솔에서 **월 사용 한도**를 설정하고, 한도 초과·API 장애 시 정적 FAQ로 대체
6. **프롬프트 인젝션**: "이전 지시를 무시하고..." 같은 입력에 대한 방어와 테스트
7. **답변 품질 검증**: 출시 전 예상 면접 질문 세트로 정확도를 점검하는 단계가 없었음
8. **응답 시점·화자 설정**: 챗봇이 1인칭("제가 구현했습니다")인지, 3인칭 안내자("지현님은 ~을 했습니다")인지 결정 필요
9. **대화 로그**: 면접관이 실제로 뭘 물었는지 보면 면접 대비에 큰 도움이 됨. 저장한다면 사이트에 고지 필요
10. **SEO/OG**: 링크 공유 시 미리보기가 중요함. Next.js(SSG) 선택 근거로 쓸 수 있음 (회고의 "SPA의 SEO" 경험과도 연결)

## 2. 기술 스택 (기본안)

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 프레임워크 | Next.js (App Router) + TypeScript | SSG로 SEO/OG 해결, Route Handler로 챗봇 서버 구현 |
| 스타일 | Tailwind CSS | 기존 사용 경험 |
| 콘텐츠 | MDX + frontmatter (zod로 스키마 검증) | 화면·챗봇 단일 원본 |
| 챗봇 | Vercel AI SDK + LLM API (스트리밍) | 채팅 UI·스트리밍 구현 간소화 |
| 요청 제한 | Upstash Redis + Ratelimit | Vercel 서버리스 환경에 적합 |
| 배포 | Vercel | Next.js 연동, 프리뷰 배포 |
| 품질 | ESLint, Prettier, (선택) Vitest/Playwright | |

## 3. 단계별 체크리스트

### Phase 0. 결정 사항 확정
- [ ] 사이트에 넣을 프로젝트 선정 (전부 / 웹·RN 중심 + iOS 일부)
- [ ] Notion 갤러리 3개 중 기준이 될 버전 결정, 중복 프로젝트 정리
- [ ] LLM 제공사·모델 결정 (Claude / OpenAI 등), API 키 발급
- [ ] 챗봇 화자 설정 (1인칭 / 3인칭 안내자)
- [ ] 사이트 언어 (한국어 / 한·영)
- [ ] 도메인 (vercel.app 기본 / 커스텀 도메인)
- [ ] 대화 로그 저장 여부
- [ ] 목표 완료일과 주당 투입 시간

### Phase 1. 콘텐츠 정리 ⭐ 가장 시간이 많이 드는 단계
- [ ] Notion 내보내기 (Markdown & CSV, 하위 페이지 포함) → 원본은 `content/_raw/`에 보관 (git 제외 검토)
- [ ] 토글 안 회고 내용이 내보내기에 포함됐는지 확인
- [ ] 이미지 정리: 파일명 영문화, WebP 변환·리사이즈, `public/projects/<slug>/`로 이동
- [ ] 프로젝트 데이터 스키마 정의 (frontmatter)
  - 화면용: `title`, `slug`, `company`, `period`, `type`(회사/사이드), `platform`(Web/iOS/RN), `stack`, `summary`, `thumbnail`, `links`
  - 챗봇용: `team`, `myRole`, `contributions`, `problemsSolved`(문제·해결·결과), `techDecisions`(선택·이유), `retrospective`, `notPublic`(말하면 안 되는 것)
- [ ] 프로젝트별 MDX 작성: **모두의 입시 AI** 먼저 (내용이 가장 풍부함)
- [ ] 나머지 프로젝트 MDX 작성 (회사 → 사이드 순)
- [ ] 각 프로젝트에 "면접에서 받을 법한 질문 3~5개 + 내 답변 요지" 추가 (챗봇 품질에 가장 큰 영향)
- [ ] 회사 프로젝트 공개 범위 검토 (내부 정보·수치 마스킹)
- [ ] 자기소개 / 기술 스택 / 경력 타임라인 / 연락처 데이터 작성

### Phase 2. 프로젝트 셋업
- [ ] Next.js + TS + Tailwind 초기화
- [ ] ESLint / Prettier / 절대경로 alias 설정
- [ ] 폴더 구조: `app/`, `components/`, `content/projects/`, `lib/`
- [ ] MDX 로더 + zod 스키마 검증 (빌드 시 누락 필드 에러)
- [ ] 브랜치 전략: `develop`에서 작업 → `main` 머지 시 배포
- [ ] Vercel 연결, 프리뷰 배포 확인
- [ ] `.env.local` / `.env.example` 구성, `.gitignore` 확인

### Phase 3. 포트폴리오 UI
- [ ] 디자인 방향 결정 (레퍼런스 2~3개 수집)
- [ ] 공통 레이아웃: 헤더, 푸터, 내비게이션
- [ ] 홈: 소개, 핵심 역량, 대표 프로젝트
- [ ] 프로젝트 목록: 카드 그리드 + 필터 (Web / iOS / RN, 회사 / 사이드)
- [ ] 프로젝트 상세 (SSG, `generateStaticParams`): 개요, 기술, 개발 사항, 회고(아코디언), 스크린샷 갤러리
- [ ] 경력 타임라인 / 기술 스택 섹션
- [ ] 이력서 PDF 다운로드, GitHub·이메일 링크
- [ ] 반응형 (모바일 우선), 다크모드
- [ ] 접근성: 시맨틱 마크업, 키보드 탐색, 이미지 alt, 색 대비
- [ ] SEO: `metadata`, OG 이미지, sitemap, robots
- [ ] `next/image`로 이미지 최적화

### Phase 4. 챗봇 서버
- [ ] `app/api/chat/route.ts` Route Handler
- [ ] 콘텐츠 → 시스템 프롬프트 직렬화 함수 (빌드 시 또는 모듈 로드 시 1회)
- [ ] 시스템 프롬프트 작성
  - [ ] 역할·화자·말투
  - [ ] 제공된 정보 안에서만 답변, 모르면 "지원자에게 직접 물어봐 달라"
  - [ ] 포트폴리오와 무관한 질문은 정중히 거절
  - [ ] `notPublic` 정보 언급 금지
  - [ ] 지시 변경 시도(프롬프트 인젝션) 무시
  - [ ] 답변 길이·형식 (짧게, 필요하면 목록)
- [ ] 프로젝트 컨텍스트 파라미터 (`projectSlug`) → 해당 프로젝트 우선 답변
- [ ] 입력 검증 (zod): 메시지 길이, 대화 턴 수 상한
- [ ] 스트리밍 응답
- [ ] 프롬프트 캐싱 적용 (시스템 프롬프트가 고정이라 비용·지연 절감 효과 큼)
- [ ] 요청 제한: IP당 분/일 한도 (Upstash)
- [ ] `max_tokens` 제한, 제공사 콘솔에서 월 사용 한도 설정
- [ ] 에러 처리: 429 / API 장애 / 한도 초과 → 사용자 메시지 + 정적 FAQ 대체
- [ ] (선택) 대화 로그 저장 (개인정보 없이 질문·답변만)

### Phase 5. 챗봇 UI
- [ ] 진입점: 플로팅 버튼 + 프로젝트 상세의 "이 프로젝트에 대해 물어보기"

- [ ] 추천 질문 칩 (전역용 / 프로젝트별)
- [ ] 스트리밍 표시, 로딩·타이핑 표시, 중단 버튼
- [ ] 마크다운 렌더링 (목록, 코드)
- [ ] 에러·요청 제한 안내 UI
- [ ] "AI가 포트폴리오를 바탕으로 생성한 답변입니다" 고지
- [ ] 접근성: 포커스 관리, `aria-live`로 응답 읽기, ESC로 닫기

### Phase 6. 품질 검증

## 4. 일정 (예시, 주 10~15시간 기준 약 5주)

| 주차 | 내용 |
| --- | --- |
| 1주 | Phase 0~1: 결정 사항 확정, 콘텐츠 정리 (대표 프로젝트 2~3개 완료) |
| 2주 | Phase 1 마무리, Phase 2 셋업, Phase 3 레이아웃·목록 |
| 3주 | Phase 3 상세 페이지·반응형·SEO, 1차 배포 (챗봇 없이도 공개 가능한 상태) |
| 4주 | Phase 4~5 챗봇 서버·UI |
| 5주 | Phase 6~8 검증, 배포, README |

> 3주 차에 챗봇 없이 먼저 배포하면, 챗봇이 늦어져도 지원에 쓸 수 있는 사이트가 확보됨.
