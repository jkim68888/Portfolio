### Q2. 면접 화면을 떠날 때 카메라 같은 리소스는 어떻게 정리하셨어요?

> 채팅 위치: modoo-ipsi-ai · 확인할 점: 본문의 라이프사이클 회고 내용

**cloud** (첫 글자 1.0초 · 전체 1.9초)

면접 세션을 떠날 때는 카메라와 마이크 스트림을 `getTracks().stop()`으로 끊고, 분석용 인터벌은 `clearInterval`로 지우고, MediaPipe 랜드마커는 `close()`로 닫도록 했습니다. 페이지를 떠난 뒤에도 카메라 LED가 켜져 있으면 사용자에게 그대로 보이기 때문에, 리소스 누수 중에서도 우선순위를 높게 두고 언마운트와 이탈 시점에 모두 정리되도록 했습니다.

**local** (첫 글자 12.1초 · 전체 15.9초 · 상세 컨텍스트: modoo-ipsi-ai)

면접 세션 라이프사이클을 모델링할 때, 언마운트나 세션 이탈 시 리소스 정리를 매우 중요하게 다뤘습니다. 저는 `getTracks().stop()`을 사용하여 카메라 스트림을 중지시키고, 분석 인터벌은 `clearInterval`로 정리했습니다. 또한, 랜드마커(`close()`)도 함께 정리하여 리소스 누수가 발생하지 않도록 했습니다. 이 과정은 사용자에게 카메라 LED가 계속 켜져 있는 상황을 방지하기 위해 우선순위를 높게 두었습니다.

### Q3. 실시간 피드백에 MediaPipe를 쓴 이유가 있나요?

> 채팅 위치: modoo-ipsi-ai

**cloud** (첫 글자 3.4초 · 전체 4.2초)

MediaPipe를 선택한 이유는 포트폴리오에 따로 정리하지 않아서, 면접에서 직접 말씀드리겠습니다. 다만 사용 방식은 말씀드릴 수 있습니다. 시선 피드백을 켰을 때만 FaceLandmarker와 PoseLandmarker를 GPU delegate로 로드해 주기적으로 분석하고, 끄면 모델을 아예 로드하지 않습니다. 기능 토글이 곧 리소스 토글이 되도록 한 것이고, 디바이스에 따라 분석 주기(데스크탑 500ms, 모바일 750ms)를 나누고 탭이 백그라운드일 때는 분석을 건너뛰도록 했습니다.

**local** (첫 글자 0.4초 · 전체 3.7초 · 상세 컨텍스트: modoo-ipsi-ai)

네, 실시간 피드백에 MediaPipe를 사용한 이유는 사용자 경험을 정교하게 개선하기 위해서였습니다. 이 기술을 통해 시선이나 자세 같은 비언어적 요소를 분석할 수 있었기 때문입니다. 특히, 시선 피드백을 켰을 때만 FaceLandmarker/PoseLandmarker를 GPU delegate로 로드하고 주기적으로 분석하도록 구현했습니다. 이렇게 기능 토글 자체가 리소스 토글이 되도록 제어하여 효율성을 높였습니다.

### Q4. 이 프로젝트에서 아쉬웠던 점은 무엇인가요?

> 채팅 위치: modoo-ipsi-ai · 확인할 점: SPA SEO 등 본문 근거

제가 진행한 '모두의 입시 AI' 프로젝트에서 아쉬웠던 점은, AI 면접 세션의 단계 전이 시 리소스 관리에 더 신경 썼어야 했다고 생각합니다. 특히 세션 이탈 시 스트림, 타이머, 랜드마커를 모두 정리하는 과정에서, 리소스 누수를 막기 위해 더 견고한 로직을 구현할 필요가 있었습니다. 또한, 결과 리포트 PDF 생성 시 픽셀 단위로 슬라이스하여 이어 붙이는 과정의 안정성을 더 높일 수 있었으면 좋았을 것 같습니다.

### Q5. 네이버 지도에서 구글맵으로 바꾼 이유는 무엇인가요?

> 채팅 위치: picaloca

**cloud** (첫 글자 0.8초 · 전체 1.6초)

v1은 한국 내 서비스 전용이라 네이버 지도 SDK를 썼는데, v2부터 해외 서비스로 확장해야 했습니다. 그런데 네이버 지도 SDK는 공식적으로 해외 지원이 되지 않아서, 글로벌 커버리지를 보장하는 Google Maps SDK로 교체했습니다. 다만 구글맵은 마커 위에 뷰를 직접 올리기 어려워서, 클러스터 렌더러에서 이미지 뷰를 직접 만들어 위치를 지정하는 방식으로 다시 구현해야 했습니다.

**local** (첫 글자 11.2초 · 전체 14.7초 · 상세 컨텍스트: picaloca)

네이버 지도에서 구글맵으로 변경한 주된 계기는 글로벌 서비스 확장이 필요했기 때문입니다. 초기 버전은 한국 내 서비스에 초점을 맞추어 네이버 지도 SDK를 사용했으나, v2 버전부터 해외 지원이 필요해졌습니다. 네이버 지도 SDK는 공식적으로 해외 지원이 불가능했기 때문에, 글로벌 커버리지를 보장하는 Google Maps SDK로 교체하기로 결정했습니다. 이 과정에서 지도 표시, 마커, 클러스터링 등의 기능을 새 SDK 기준으로 재구현했습니다.

**local** (첫 글자 10.9초 · 전체 14.1초 · 상세 컨텍스트: picaloca)

지도에서 게시물 조회 API 호출을 최적화하기 위해 호출 조건을 명확히 정리했습니다. 처음에는 지도 상태가 바뀔 때마다 API를 호출하여 요청이 반복되었고, 이는 서버 부하와 UI 깜빡임 문제를 일으켰습니다. 개선 후에는 카메라 위치가 바뀌었을 때와 같은 위치에서 줌 아웃할 때만 요청하도록 조건을 정했습니다. 이로써 불필요한 API 요청을 줄이고 안정적인 사용자 경험을 제공할 수 있었습니다.

### Q9. 웹뷰 쿠키는 왜 다뤄야 했나요?

> 채팅 위치: saving-hanaro · 확인할 점: 마케팅 유입 유저 판별

**cloud** (첫 글자 1.8초 · 전체 3.1초)

저축하나로 앱은 React 웹을 WKWebView로 감싼 구조라, 웹에서 생긴 쿠키를 네이티브에서도 다룰 필요가 있었습니다. 가장 큰 이유는 마케팅 링크로 들어온 유저를 구분해 마케팅 성과를 측정해야 했기 때문입니다. 그래서 마케팅 링크로 들어온 유저라는 정보를 쿠키에 저장하고, 딥링크로 앱이 열리면 그 쿠키를 조회해 유입 유저인지 판단하도록 했습니다. 이를 위해 WKHTTPCookieStore를 이용한 쿠키 조회·저장·삭제 기능을 WKWebView 확장으로 묶어 재사용할 수 있게 만들었습니다.

**local** (첫 글자 2.7초 · 전체 5.6초 · 상세 컨텍스트: saving-hanaro)

저축하나로 프로젝트에서 쿠키를 다룬 이유는 마케팅 성과를 측정하기 위해서였습니다. 구체적으로는 마케팅 링크를 통해 유입된 사용자를 구분하는 데 활용해야 했기 때문입니다. 저는 WKHTTPCookieStore를 활용하여 웹뷰의 기본 데이터 저장소에 있는 쿠키를 조회하고 저장하는 기능을 구현했습니다. 이 기능을 통해 마케팅 유입 유저라는 정보를 쿠키에 저장하고, 딥링크로 앱이 열릴 때 이 값을 조회하여 유입 여부를 판단했습니다.
