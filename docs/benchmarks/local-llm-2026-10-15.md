이러한 방법들을 통해 사용자 경험을 개선하고 시스템 리소스를 효율적으로 관리할 수 있었습니다. 만약 구체적인 코드 예시나 더 자세한 구현 방법이 필요하시다면, 해당 프로젝트의 상세 페이지를 참조해 주시거나 직접 물어봐 주시면 자세히 설명드릴 수 있습니다.

SPA의 SEO 문제를 해결하기 위해 다음과 같은 방법들을 적용했습니다:

- **동적 `<title>` 및 `robots` 메타 태그 관리**: 각 라우트 경로에 따라 동적으로 `<title>` 태그와 `robots` 메타 태그를 변경했습니다. 이를 통해 검색 엔진이 각 페이지의 내용을 정확하게 이해하고 인덱싱할 수 있도록 했습니다.
  
- **정적 `index.html` 활용**: 기본적인 페이지 정보는 정적 `index.html` 파일에 설정하여 검색 엔진이 초기 페이지 구조를 인식할 수 있도록 했습니다.

- **사이트맵 관리**: sitemap을 통해 공개된 페이지들을 명시적으로 관리하여 검색 엔진이 전체 사이트 구조를 더 잘 이해하고 크롤링할 수 있도록 지원했습니다.

이러한 접근법을 통해 검색 엔진이 SPA의 동적 콘텐츠와 라우팅 구조를 효과적으로 처리하고 인덱싱할 수 있도록 했습니다. 이렇게 하면 사용자 경험뿐만 아니라 검색 엔진 최적화(SEO) 측면에서도 균형을 맞출 수 있었습니다.

### 5. MVC에서 클린 아키텍처로 리팩토링한 이유와 효과가 궁금합니다.

네, 피카로카 프로젝트에서 MVC 패턴에서 클린 아키텍처로 리팩토링한 이유와 효과에 대해 자세히 설명드리겠습니다.

### 리팩토링 이유

1. **유지보수성 향상**: 초기 개발 단계에서는 빠른 출시를 위해 **MVC 패턴**을 사용했습니다. 하지만 프로젝트가 복잡해지면서 **ViewController에 비즈니스 로직과 데이터 처리 코드가 혼재**되어 유지보수가 어려워졌습니다. 특히 기능이 추가되거나 수정될 때마다 코드베이스가 복잡해져 관리가 어려워졌습니다.

2. **확장성 문제**: 기존 구조에서는 새로운 기능을 추가하거나 기존 기능을 수정할 때 **ViewController에 직접 로직을 추가**해야 하는 경우가 많았습니다. 이로 인해 코드의 중복과 복잡성이 증가했습니다. 클린 아키텍처로의 전환은 각 계층의 책임을 명확히 분리하여 확장성을 크게 향상시켰습니다.

3. **테스트 용이성**: MVC 구조에서는 테스트를 작성하기 어려웠습니다. 반면 클린 아키텍처는 **테스트 용이성**을 크게 향상시킵니다. 각 계층이 독립적으로 작동하도록 설계되어 단위 테스트를 쉽게 작성할 수 있게 되었습니다.

### 리팩토링 효과

1. **관심사 분리**: **View와 비즈니스 로직을 명확히 분리**하여 코드의 가독성과 유지보수성이 크게 향상되었습니다. 각 계층이 특정 역할에 집중하므로 개발자가 특정 부분을 수정하거나 이해하는 데 훨씬 용이해졌습니다.

2. **비동기 처리의 간결화**: **RxSwift**를 도입함으로써 비동기 처리가 더 직관적이고 선언적으로 이루어지게 되었습니다. 이전의 Delegate 패턴이나 Callback 방식에 비해 코드가 더 간결해지고 이해하기 쉬워졌습니다.

3. **성능 개선**: **클라이언트 측에서의 데이터 처리와 서버 측의 데이터 처리를 명확히 구분**함으로써 앱의 성능이 개선되었습니다. 특히 지도 관련 기능에서 클러스터링과 같은 복잡한 로직이 더 효율적으로 처리될 수 있었습니다.

4. **확장성 향상**: 각 계층의 책임이 명확해지면서 새로운 기능을 추가하거나 기존 기능을 수정할 때 영향 범위가 최소화되었습니다. 이로 인해 프로젝트의 확장성이 크게 향상되었습니다.

이러한 변화를 통해 피카로카 앱은 더 안정적이고 확장 가능한 구조로 발전할 수 있었습니다.

### 7. 웹뷰와 네이티브 사이의 JS 브릿지는 어떻게 구현하셨나요?

> 맥락: saving-hanaro
> 첫 글자 4.4초 · 전체 29.0초 · 입력 1613 토큰(4.2초) · 출력 551 토큰 · 22.4 tok/s

저축하나로 프로젝트에서 웹뷰와 네이티브 앱 사이의 JS 브릿지는 주로 `WKScriptMessageHandler`를 활용하여 구현했습니다. 구체적인 과정은 다음과 같습니다:

1. **WKUserContentController 설정**: 웹뷰에서 메시지를 수신할 핸들러를 등록하기 위해 `WKUserContentController`를 설정합니다.
   
   ```swift
   let contentController = WKUserContentController()
   ```

2. **WKWebView 구성**: 웹뷰의 구성을 설정하고 사용자 콘텐츠 컨트롤러를 연결합니다.
   
   ```swift
   let configuration = WKWebViewConfiguration()
   configuration.userContentController = contentController
   defaultWebView = WKWebView(frame: .zero, configuration: configuration)
   ```

3. **메시지 핸들러 등록**: 특정 이름의 메시지 핸들러를 등록하여 웹페이지에서 네이티브 코드로 메시지를 전송할 수 있게 합니다.
   
   ```swift
   contentController.add(self, name: "appleLoginBtnClick")
   ```

4. **메시지 수신 처리**: `WKScriptMessageHandler` 프로토콜을 채택하여 메시지를 수신하고 처리하는 메소드를 구현합니다.
   
   ```swift
   extension ViewController: WKScriptMessageHandler {
       func userContentController(_ userContentController: WKUserContentController, didReceive message: WKScriptMessage) {
           if message.name == "appleLoginBtnClick" {
               // 애플 로그인 처리 로직
               handleAppleLogin(message: message.body)
           }
       }
       
       private func handleAppleLogin(message: Any) {
           // 애플 로그인 관련 로직 구현
           // 메시지 내용을 통해 필요한 데이터를 추출
       }
   }
   ```

5. **웹페이지에서의 메시지 전송**: 웹페이지 측에서는 JavaScript를 통해 네이티브 코드로 메시지를 전송합니다.
   
   ```javascript
   function handleAppleLogin() {
       window.webkit.messageHandlers.appleLoginBtnClick.postMessage({
           action: 'startAppleLogin',
           redirectUrl: 'https://example.com/callback'
       });
   }
   ```

이렇게 구현하면 웹페이지에서 네이티브 앱으로 메시지를 보내고, 네이티브 앱에서 해당 메시지를 처리하여 애플 로그인 등의 기능을 구현할 수 있습니다. 이 방식은 양방향 통신을 가능하게 하여 사용자 경험을 향상시키는 데 효과적입니다.

1. **대기 시간**: 무료 플랜을 사용할 때 특히 클라우드 빌드 대기 시간이 길어질 수 있었습니다. 이로 인해 빠른 피드백 루프를 유지하는 데 약간의 어려움이 있었습니다.

2. **설정 복잡성**: `eas.json` 파일을 적절히 구성하는 과정에서 초기 설정이 다소 복잡하게 느껴졌습니다. 특히 다양한 환경 설정(개발, 프리뷰, 프로덕션 채널)을 올바르게 분리하고 구성하는 데 시간이 조금 걸렸습니다.

3. **자동화 스크립트**: CI/CD 파이프라인과의 통합은 매우 편리했지만, 스크립트 작성 시 일부 세부 설정이 예상과 다르게 동작할 때가 있어 디버깅이 필요했습니다.

이러한 문제들에도 불구하고, EAS Build의 장점들이 많은 도움이 되어 개발 효율성을 크게 향상시킬 수 있었습니다. 특히 로컬 환경 구축이 필요 없고, OTA 업데이트와 채널 기반 배포가 용이하다는 점은 큰 장점이었습니다. 만약 더 구체적인 사항이나 특정 문제에 대해 궁금하시다면 말씀해 주세요!
